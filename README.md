# Reploom — база данных

Локальная PostgreSQL-база для Next.js + Spring Boot. Полная текущая логическая модель: **67 предметных таблиц**, миграции **V1–V9**, Flyway и интеграционные проверки. Backend пока не создан.

## Первый запуск

Нужны Docker Desktop с Linux-контейнерами и Python 3.10+ для команд управления.

1. Скопируйте `.env.example` в `.env` и задайте уникальный `POSTGRES_PASSWORD`.
2. Выполните из корня `project`:

```powershell
docker compose up -d postgres
python database/manage.py migrate
python database/manage.py validate
python database/manage.py provision-runtime
```

Данные сохраняются в Docker volume. Локальный порт: `127.0.0.1:5433` по умолчанию. Менять пароль существующей роли нужно в PostgreSQL; изменение `.env` само по себе его не меняет.

## Повседневные команды

```powershell
python database/manage.py info
python database/manage.py validate
python database/manage.py backup
python database/manage.py verify
docker compose stop
```

`verify` создаёт две базы с уникальными именами `reploom_check_*`, разворачивает миграции, выполняет сценарии с искусственными данными, создаёт custom-format dump, восстанавливает его и сравнивает отпечатки всех строк всех public-таблиц. Созданные этой командой базы удаляются в конце; основная база не изменяется. Проверочный архив остаётся в игнорируемой папке `database/backups/`. Отчёт: `database/verification.json`.

`backup` создаёт резервную копию основной базы. Архив содержит персональные данные при их наличии: храните его вне Git и переносите копии на отдельный носитель/хранилище. `docker compose down -v` удаляет том PostgreSQL — не используйте эту команду для обычной остановки.

## Подключение Spring Boot

Использовать `APP_DB_USER` и `APP_DB_PASSWORD` из локального `.env`. Команда `provision-runtime` создаёт отдельную LOGIN-роль без superuser, DDL и bypass RLS; пароли в консоль не выводятся. Для миграций используются административные настройки `POSTGRES_*`.

Адрес при запуске Java на компьютере: `jdbc:postgresql://localhost:5433/reploom`. В Docker-сети проекта: `jdbc:postgresql://postgres:5432/reploom`.

**Каждая транзакция пользовательской операции должна установить доверенный контекст:**

```sql
SELECT set_config('reploom.user_id', :authenticated_user_uuid, true);
```

UUID берётся сервером из проверенной аутентификации. Его нельзя принимать как доказательство прав из тела запроса. Параметр `true` ограничивает контекст текущей транзакцией и предотвращает утечку между пользователями в пуле подключений. Без контекста runtime-роль не видит персональные записи. Учётные данные БД никогда не выдавать браузеру. RLS дополняет серверную авторизацию, не заменяет её и не защищает от злоумышленника с возможностью выполнять произвольный SQL от runtime-роли.

Hibernate должен проверять схему (`ddl-auto=validate`), а не менять её. Миграции при деплое запускаются отдельным заданием с административными реквизитами; backend запускается с runtime-реквизитами. Копию SQL из `database/migrations/` не дублировать в другой папке без единого процесса сборки.

## Порядок операций

- Шаблон/программу создать как DRAFT, заполнить состав, затем опубликовать. Опубликованные версии и дочерние строки неизменяемы.
- Изменение упражнения с другой схемой измерений оформлять новым движением. Замену движения в активной сессии — новой строкой упражнения и подходов, не переписыванием старой строки.
- Источник сессии фиксируется при старте. Скопировать план, названия и схему измерений в строки сессии должен backend, в одной транзакции со стартом.
- Для DROP/CLUSTER значения записываются в сегменты; родитель не дублирует количественные показатели. В плане минимум два сегмента. В выполненном подходе — минимум два сегмента и хотя бы один выполненный.
- Частичное завершение допустимо; пустая сессия отменяется. Завершённая сессия имеет хотя бы один выполненный подход.
- Для исправления завершённого результата использовать `reploom_correct_set(set_id, patch_json, reason, expected_revision)` или `reploom_correct_segment(...)`. Эти функции проверяют владельца, конфликт ревизии и значения, сохраняют diff и инвалидируют производную аналитику. Прямое изменение завершённого факта запрещено.
- Пищевые снимки и эффективный план с корректировками материализует backend. Периоды дневных целей не могут пересекаться.
- AI-применение требует записанного ACCEPT; проверяется версия назначения для точечных корректировок. Модель не подключается к БД. Контекст, полноту предложения, ограничения нагрузок и выбор целевого типа проверяет backend.
- Действуют отложенные проверки на конец транзакции: строки приёма пищи и его состав, публикация и минимальное наполнение, группировки. Используйте транзакции; не сохраняйте эти объекты по отдельным autocommit-запросам.

## Резервные копии и перенос

Для восстановления custom-format архива используйте `pg_restore --exit-on-error --no-owner` в отдельную пустую базу. До переноса на другой сервер должна существовать NOLOGIN-роль `reploom_app`; LOGIN-роль и пароль создаются отдельно. Пароли LOGIN-ролей не входят в дамп одной базы. Не восстанавливайте тестовый архив поверх основной базы.

Для production дополнительно выбрать управляемый PostgreSQL или настроить сервер, TLS, закрытую сеть, автоматические резервные копии с согласованными RPO/RTO, мониторинг и проверку восстановления. Тест восстановления здесь проверяет локальный логический dump, а не аварийное восстановление всего сервера.

## Git

Коммитить: `.env.example`, `.gitignore`, `compose.yaml`, `README.md`, `database/migrations/`, `database/tests/`, `database/manage.py`, `database/verification.json`.

Не коммитить: `.env`, дампы, Docker volume и пароли. Obsidian находится в соседней папке `../Obsidian model/`, вне этого Git-репозитория; его изменения сохраняются отдельно.
